# 工場設備ネットワークをWi-Fiで順番に切り替えてデータ収集する基礎仕様

## 1. 目的

工場内に複数の独立した設備ネットワークが存在し、それぞれの設備から1台の監視PCで定期的にデータを収集する。

今回の方式では、各設備の既存ネットワーク構成やIPアドレスを極力変更せず、各設備にWi-Fiアクセスポイントを追加する。

監視PCは1個のWi-Fiアダプターを使用し、接続先SSIDをPythonから順番に切り替える。

想定用途はリアルタイム制御ではなく、数分ごとの巡回データ収集である。

------------------------------------------------------------------------

## 2. 基本となる設備構成

各設備には、たとえば次の機器が存在する。

-   PLC
-   タッチパネル
-   監視・計測機器
-   Ethernet用HUB
-   監視用PCから接続するためのWi-Fiアクセスポイント

既存設備ではPLCやタッチパネルは有線LANのままとする。

``` text
PLC ─────────┐
              │
タッチパネル ─┼─ HUB ─ Wi-Fiアクセスポイント
              │              )))
その他機器 ───┘              ))) Wi-Fi
                             )))
```

Wi-Fi化するのは、基本的に「外部の監視PCから設備ネットワークへ入る部分」だけである。

PLCとタッチパネル間など、設備制御に関係する通信まで無線化する必要はない。

------------------------------------------------------------------------

## 3. インターネット接続は不要

今回使用するWi-Fiは、インターネットへ接続するためのものではない。

Wi-Fiは単純に、

``` text
有線Ethernet
      ↓
Wi-Fiアクセスポイント
      ↓
無線LAN
      ↓
監視PC
```

という「LANケーブルの一部分を無線化する仕組み」として使用する。

したがって、

``` text
インターネット
      ×

PLC ─ HUB ─ Wi-Fi AP ))) 監視PC
 │
TP
```

という完全に閉じたネットワークで運用できる。

------------------------------------------------------------------------

## 4. 開発段階では民生用Wi-Fiルーターを使用できる

開発・検証段階では、高価な産業用アクセスポイントを使用する必要はない。

一般家庭向けのWi-Fiルーターでも、

-   APモード
-   アクセスポイントモード
-   ブリッジモード
-   BRモード

などに対応していれば使用できる。

重要なのは、Wi-Fiルーターを「ルーター」として使用するのではなく、

**有線LANと無線LANを橋渡しするアクセスポイントとして使用すること**

である。

基本構成は次のようになる。

``` text
PLC ─────────┐
              │
タッチパネル ─┼─ HUB ─ LAN ─ Wi-Fiルーター
              │               （APモード）
              │                    )))
              │                    ))) Wi-Fi
              │                    )))
              │                 監視PC
```

開発用であれば、BUFFALO、TP-Link、NEC
Aterm、ELECOMなどの一般的な製品で十分検証できる。

実際の工場で長期間運用する段階になったら、必要に応じて産業用アクセスポイントへの変更を検討する。

------------------------------------------------------------------------

## 5. PCにWi-Fiがなくても問題ない

監視PCにWi-Fi機能が内蔵されていない場合は、USB
Wi-Fiアダプターを使用できる。

``` text
Wi-Fi AP
   )))
   )))
USB Wi-Fiアダプター
        │
      監視PC
```

したがって、既存のデスクトップPCや設備用PCでも後からWi-Fi機能を追加できる。

工場では金属製の設備や制御盤によって電波が遮られることがあるため、本運用ではアンテナ付き製品やUSB延長ケーブルなどを利用して、アンテナ位置を調整できる構成も有効である。

------------------------------------------------------------------------

## 6. 複数設備を1台のPCから巡回する

今回の重要な考え方である。

設備ごとに独立したWi-Fiアクセスポイントを設置し、それぞれ異なるSSIDを設定する。

例：

``` text
設備1
PLC ─ HUB ─ AP
            SSID: MACHINE_01
                 )))

設備2
PLC ─ HUB ─ AP
            SSID: MACHINE_02
                 )))

設備3
PLC ─ HUB ─ AP
            SSID: MACHINE_03
                 )))
```

監視PCにはWi-Fiアダプターを1個だけ取り付ける。

``` text
MACHINE_01 ))) ┐
MACHINE_02 ))) ├── Wi-Fiアダプター × 1 ── 監視PC
MACHINE_03 ))) ┘
```

監視PCは複数の設備へ同時接続するのではなく、順番に接続する。

``` text
設備1へ接続
    ↓
データ取得
    ↓
設備2へ切り替え
    ↓
データ取得
    ↓
設備3へ切り替え
    ↓
データ取得
    ↓
設備1へ戻る
```

数分ごとのデータ収集であれば、この方式で十分実用的である。

------------------------------------------------------------------------

## 7. PythonからWi-Fi接続先を切り替える

Windowsでは標準の `netsh` コマンドを利用してWi-Fi接続先を変更できる。

あらかじめWindowsに各SSIDのWi-Fiプロファイルを登録しておく。

コマンド例：

``` text
netsh wlan connect name="MACHINE_01"
```

Pythonからは `subprocess` を利用できる。

``` python
import subprocess


def connect_wifi(ssid: str) -> None:
    subprocess.run(
        [
            "netsh",
            "wlan",
            "connect",
            f"name={ssid}",
        ],
        check=True,
    )


connect_wifi("MACHINE_01")
```

設備2へ変更する場合は、

``` python
connect_wifi("MACHINE_02")
```

とすればよい。

------------------------------------------------------------------------

## 8. Wi-Fi切り替え直後にPLC通信を開始しない

ここは実装上重要である。

`netsh wlan connect`
が実行できたからといって、その瞬間にPLCとの通信が可能になっているとは限らない。

実際には、

``` text
PythonからWi-Fi接続命令
        ↓
Windowsが接続先を変更
        ↓
Wi-Fi接続確立
        ↓
ネットワーク使用可能
        ↓
PLCへ疎通確認
        ↓
PLCデータ取得
```

という時間差がある。

したがって実際のプログラムでは、

``` python
connect_wifi("MACHINE_01")

wait_until_connected("MACHINE_01")

wait_until_plc_reachable()

data = read_plc()
```

のような構造にする。

単純な固定 `sleep()` だけでも試験はできるが、本運用では、

-   目的のSSIDへ接続されたか
-   Wi-Fiインターフェースが使用可能か
-   PLCへ通信できるか

を確認してからデータ取得を開始する方が堅牢である。

------------------------------------------------------------------------

## 9. 各設備のネットワークアドレスが同じでもよい

今回の方式の非常に大きなメリットである。

設備がそれぞれ物理的・論理的に独立している場合、各設備で同じIPアドレスを使用できる。

例：

``` text
【設備1】

ネットワーク    192.168.1.0/24
PLC             192.168.1.10
タッチパネル     192.168.1.20
その他機器       192.168.1.30
AP              192.168.1.100


【設備2】

ネットワーク    192.168.1.0/24
PLC             192.168.1.10
タッチパネル     192.168.1.20
その他機器       192.168.1.30
AP              192.168.1.100
```

設備1と設備2は同時に同じLANへ接続されていないため、IPアドレスの重複は問題にならない。

監視PCから見ると、

``` text
MACHINE_01へ接続
        ↓
192.168.1.10 = 設備1のPLC
        ↓
データ取得


MACHINE_02へ切り替え
        ↓
192.168.1.10 = 設備2のPLC
        ↓
データ取得
```

となる。

したがってPython側のPLCアドレスも共通化できる。

``` python
PLC_IP = "192.168.1.10"
```

設備によって変更する必要があるのは、基本的には接続先SSIDだけである。

------------------------------------------------------------------------

## 10. 設備側のIPアドレスを変更しなくてよい

工場設備では、PLC、タッチパネル、画像処理装置、計測器などのIPアドレスが設備設計時に決められていることが多い。

既存設備のIPアドレスを後から変更すると、

-   PLC設定
-   タッチパネル設定
-   PLCプログラム
-   通信機器設定
-   画像処理装置
-   保守資料

など、多数の場所へ影響する可能性がある。

今回の方式では設備ネットワーク自体を変更する必要がない。

``` text
既存設備

PLC 192.168.1.10
TP  192.168.1.20
        │
       HUB
        │
      AP追加
```

という後付けが可能である。

これは既存設備のデータ収集では非常に大きなメリットになる。

------------------------------------------------------------------------

## 11. 設備識別はSSIDとは別の設定値を持たせる

PLCのIPアドレスが全設備共通でも、収集したデータには「どの設備から取得したか」という識別情報が必要である。

例えば設定を次のようにする。

``` python
MACHINES = [
    {
        "machine_no": 1,
        "ssid": "MACHINE_01",
    },
    {
        "machine_no": 2,
        "ssid": "MACHINE_02",
    },
    {
        "machine_no": 3,
        "ssid": "MACHINE_03",
    },
]
```

そして、

``` python
PLC_IP = "192.168.1.10"


for machine in MACHINES:
    connect_wifi(machine["ssid"])

    # 接続完了確認
    # PLC疎通確認

    data = read_plc(PLC_IP)

    save_data(
        machine_no=machine["machine_no"],
        data=data,
    )
```

という構造にできる。

SSIDそのものを設備識別子として利用することも可能だが、将来SSIDを変更する可能性を考えると、`machine_no`
などの独立した設備識別子を持たせる方が扱いやすい。

------------------------------------------------------------------------

## 12. PC側のIPアドレス

設備ネットワークがすべて同じ構成なら、監視PC側も同じ固定IPを使用できる。

例：

``` text
PLC             192.168.1.10
タッチパネル     192.168.1.20
監視PC           192.168.1.200
サブネットマスク 255.255.255.0
```

監視PCのWi-Fiインターフェースを `192.168.1.200/24`
に固定しておけば、接続先APを切り替えてもPC側のIP設定を変更する必要がない。

設備LANが閉じたネットワークで、インターネットへのルーティングを必要としない場合は、通常デフォルトゲートウェイを設定する必要もない。

ただし、実際の設備ネットワークに既に `192.168.1.200`
を使用している機器が存在しないことを必ず確認する。

------------------------------------------------------------------------

## 13. 同じネットワークを同時接続してはいけない

今回の方式が成立する重要な条件である。

例えば設備1と設備2の両方が、

``` text
192.168.1.0/24
```

を使用している場合、PCが両方へ同時接続すると問題になる。

``` text
設備1 PLC 192.168.1.10 ─┐
                          ├─ PC
設備2 PLC 192.168.1.10 ─┘
```

PCから見ると、

``` text
192.168.1.10
```

がどちらのPLCなのか一意に決められない。

そのため今回の方式では、

**Wi-Fiアダプター1個で1設備ずつ接続する**

ことが重要である。

``` text
設備1 接続
設備2 切断
設備3 切断

      ↓

設備1 切断
設備2 接続
設備3 切断

      ↓

設備1 切断
設備2 切断
設備3 接続
```

これによって同一IPアドレス体系の設備を安全に巡回できる。

------------------------------------------------------------------------

## 14. 有線LANとの違い

単純に各設備を有線HUBでまとめると、同じIPアドレスを持つ機器が同じネットワーク上に存在してしまう。

``` text
設備1 PLC 192.168.1.10 ─┐
設備2 PLC 192.168.1.10 ─┼─ HUB ─ PC
設備3 PLC 192.168.1.10 ─┘
```

これは使用できない。

有線で同様のことを実現する場合は、

-   複数NIC
-   LAN切替器
-   VLAN
-   ルーター
-   NAT
-   ネットワーク分離

などが必要になる。

Wi-Fi方式では、

**「接続するSSIDを変更すること」が物理的なLAN切り替えの役割を果たす**

ため、1個のWi-Fiアダプターで複数の独立設備ネットワークを巡回できる。

これは今回の用途におけるWi-Fiの大きなメリットである。

------------------------------------------------------------------------

## 15. リアルタイム監視には向かない

Wi-Fiアダプター1個の場合、基本的には1つのAPへ接続している間、他の設備とは通信できない。

したがって、

``` text
設備1を監視しながら
設備2も同時にリアルタイム監視
```

という用途には向かない。

一方、

``` text
5分ごとに各設備からデータを取得
```

のような用途には非常に適している。

今回の前提は、

**リアルタイム制御ではなく、数分単位の巡回データ収集**

である。

------------------------------------------------------------------------

``` text
  ▼

  │
  ▼

  │
  ▼

  │

  │
  └──────────────→ START
```

## 17. エラー処理も重要

実際の工場では、すべての設備へ必ず接続できるとは限らない。

例えば、

-   APの電源が切れている
-   設備自体の電源が切れている
-   電波が弱い
-   PLCが停止している
-   Wi-Fi接続に失敗した
-   PLC通信がタイムアウトした

などが考えられる。

したがって、

``` text
設備1
 ↓
成功
 ↓
設備2
 ↓
接続失敗
 ↓
ログ記録
 ↓
設備3へ進む
```

という設計が望ましい。

1台の設備への接続失敗によって、巡回処理全体を停止させない。

概念的には、

``` python
for machine in MACHINES:
    try:
        connect_wifi(machine["ssid"])

        wait_until_connected(machine["ssid"])

        data = read_plc(PLC_IP)

        save_data(machine["machine_no"], data)

    except Exception as error:
        log_error(machine["machine_no"], error)

        continue
```

のような構造になる。

------------------------------------------------------------------------

## 18. Wi-Fi切り替え時間を考慮する

設備数が増えると、データ取得時間よりもWi-Fiの接続切り替え時間の方が支配的になる可能性がある。

例えば仮に、

``` text
Wi-Fi切り替え・確認   5秒
PLCデータ取得         1秒
保存                  0.1秒
```

なら、1設備あたり約6秒になる。

10設備なら約60秒で1巡できる。

実際の時間はAP、USB
Wi-Fiアダプター、Windows、電波状況などによって変わるため、開発段階で実測する。

今回の用途が「数分ごと」であれば、多少の切り替え時間は十分許容できる可能性が高い。

## 19. 工場での注意点

民生用Wi-Fi機器で開発できても、本番環境では次の点を確認する。

### 電波環境

工場には、

-   金属製設備
-   制御盤
-   モーター
-   インバーター
-   大型機械
-   壁
-   他のWi-Fi設備

などが存在する。

家庭よりも電波環境が厳しい場合がある。

### アンテナ位置

APやUSB
Wi-Fiアダプターを金属盤の内部や設備の奥に置くと、通信品質が悪化する可能性がある。

アンテナ位置を調整できる構成が望ましい。

### 長時間運転

開発時に短時間動作しただけでは、本番運用の安定性は判断できない。

長時間の連続運転試験を行う。

### 制御には使用しない

今回のWi-Fi経路は監視・データ収集用とする。

設備を停止させる、安全装置を動作させる、といった重要なリアルタイム制御をこの方式へ依存させない。

------------------------------------------------------------------------

## 20. 開発段階と本番段階

### 開発段階

低コストで試験する。

``` text
家庭用Wi-Fiルーター
        +
USB Wi-Fiアダプター
        +
Windows PC
        +
Python
```

まず確認するのは、

-   PythonからSSIDを切り替えられるか
-   切り替え後にPLCへ接続できるか
-   同じPLC IPで複数設備を巡回できるか
-   Wi-Fi切り替えに何秒かかるか
-   通信失敗時に次の設備へ進めるか

などである。

### 本番段階

開発結果をもとに、

-   民生用APのままで問題ないか
-   産業用APへ変更するか
-   アンテナ位置
-   電波強度
-   電源
-   ノイズ
-   耐環境性
-   長時間安定性

を検討する。

ネットワーク方式自体は同じなので、民生用APから産業用APへ変更しても、Python側の基本設計はほぼ変更しなくてよい。

------------------------------------------------------------------------

## 21. この方式の大きなメリット

今回の方式をまとめると、次の特徴がある。

1.  既存PLCのIPアドレスを変更しなくてよい
2.  タッチパネルの設定を変更しなくてよい
3.  各設備で同じネットワークアドレスを使用できる
4.  各設備のネットワークを独立したまま維持できる
5.  監視PCは1台でよい
6.  Wi-Fiアダプターも基本的に1個でよい
7.  配線工事を大幅に減らせる
8.  Pythonから自動的に設備を巡回できる
9.  既存設備への後付けがしやすい
10. 開発段階は安価な民生機器で検証できる
11. 必要なら本番だけ産業用APへ変更できる

特に重要なのは、

> **設備側を監視PCの都合に合わせるのではなく、監視PCの方から各設備の既存ネットワークへ順番に入りに行く**

という考え方である。

``` text

PLC
 │
TP
 │
その他Ethernet機器
 │

 │

```

各設備のIP構成は共通でもよい。

``` text
PLC       192.168.1.10
TP        192.168.1.20

```

SSIDだけ設備ごとに分ける。

``` text
設備1 → MACHINE_01

```

監視PC：

``` text

   │
```

``` text
MACHINE_01
   ↓
PLCデータ取得
   ↓
MACHINE_02
   ↓

   ↓
MACHINE_03
   ↓
PLCデータ取得
   ↓
MACHINE_04
   ↓
PLCデータ取得
   ↓
一定時間待機
   ↓
繰り返し
```

## 23. 今後の実装ステップ

次に実際の検証を行う場合は、いきなりPLC通信まで作り込まず、段階的に確認すると分かりやすい。

### STEP 1

Wi-Fi APを2台用意する。

``` text
MACHINE_01
MACHINE_02
```

### STEP 2

Windowsから手動でSSIDを切り替えられることを確認する。

### STEP 3

`netsh wlan connect` でコマンドラインから切り替える。

### STEP 4

Pythonの `subprocess` から切り替える。

### STEP 5

Pythonから現在接続しているSSIDを確認する。

### STEP 6

各設備のPLCへPingまたはTCP通信で疎通確認する。

### STEP 7

PLCデータを実際に取得する。

### STEP 8

設備1 → 設備2 → 設備1の自動巡回を作る。

### STEP 9

通信失敗、AP電源OFFなどの異常試験を行う。

### STEP 10

SQLiteへの保存まで組み込み、複数設備の巡回収集システムへ発展させる。

## 24. まとめ

今回の方式では、各設備の既存ネットワークをそのまま維持しながら、Wi-Fiアクセスポイントを追加するだけで1台の監視PCから複数設備を巡回できる。

特に、

``` text
設備1 PLC = 192.168.1.10
設備2 PLC = 192.168.1.10
設備3 PLC = 192.168.1.10
```

のように各設備で同じIPアドレスを使用していても、

``` text
MACHINE_01へ接続
      ↓
データ取得
      ↓
MACHINE_02へ接続
      ↓
データ取得
```

と1ネットワークずつ切り替えることで扱える。

この方式は、

**「各設備を中央ネットワークへ統合する」のではなく、「1台の収集PCが独立した設備ネットワークを順番に訪問する」**

という考え方である。

既存設備の設定変更を最小限にできるため、工場に既に多数存在する独立設備から、数分間隔でデータを収集する用途に適している。

今後の重要な技術要素は、

-   PythonによるSSID切り替え
-   接続完了判定
-   PLC疎通確認
-   タイムアウト処理
-   失敗時のスキップ
-   ログ記録
-   巡回スケジュール
-   SQLiteへの設備番号付き保存

である。

まずは家庭用Wi-Fiルーター2台とUSB
Wi-Fiアダプター1個程度の小さな構成で実証し、安定性と切り替え時間を確認してから設備数を増やしていくのがよい。
