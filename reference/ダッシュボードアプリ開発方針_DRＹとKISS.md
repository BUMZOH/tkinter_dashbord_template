# ダッシュボードアプリ開発方針

## ― DRYとKISSのバランス、テンプレートを活用した「独立ページ方式」 ―

## 1. はじめに

今回のダッシュボード改造を通して、今後のアプリ開発で基礎にしたい方針が明確になった。

最初の課題は、Chart や Table
を持つページが増えたときに、似たコードが大量に増えることであった。

一般的には「重複をなくす（DRY）」ために共通関数や共通クラスを作る方向へ進みやすい。

しかし、共通化を進めすぎると次の問題が起こる。

-   コードを見ただけでは具体的な画面が想像しにくい
-   引数や設定項目が増える
-   1ページだけ変更したい場合でも共通部分への影響を考える必要がある
-   VS Code の補完を使いながら素直にコードを追いにくくなる
-   「どこを直せばよいのか」が分かりにくくなる
-   将来の変更に備えた抽象化が、現在の開発を難しくする

そこで今回たどり着いた基本方針は、

> **共通化するために複雑にしない。ページ単位で独立させ、良いテンプレートを安全にコピーして使う。**

という考え方である。

------------------------------------------------------------------------

## 2. 最重要方針：KISSを優先する

KISS は **Keep It Simple, Stupid** の略である。

今回の開発では、単にコード行数を減らすことよりも、

-   読んですぐ分かる
-   修正場所がすぐ分かる
-   VS Code の補完が効く
-   具体的な画面を想像しやすい
-   数か月後の自分でも理解できる

ことを重視する。

コードが10行短くなっても、理解するために頭の中で複数ファイルや設定を追いかける必要があるなら、必ずしも「シンプル」ではない。

**短いコードと、分かりやすいコードは同じではない。**

------------------------------------------------------------------------

## 3. DRYは重要だが、絶対ではない

DRY は **Don't Repeat
Yourself**、つまり「同じ知識や処理を重複させない」という考え方である。

もちろんDRYは重要である。

しかし、

> **重複コードが存在すること自体を悪としない。**

特にGUIアプリでは、似ているように見えるページでも、後から少しずつ仕様が変わることが多い。

例えば、

-   日別ページだけグラフを変更したい
-   アラーム別ページだけ検索条件を追加したい
-   生産実績ページだけTableの列を増やしたい
-   あるページだけボタンを追加したい

といった変更が発生する。

最初からすべてを共通化すると、この「ページごとの差」が共通クラスの大量の引数や条件分岐になりやすい。

その結果、

``` python
create_dashboard_tab(
    chart_type="bar",
    x_column="date",
    y_column="alarm_count",
    horizontal=False,
    show_table=True,
    ...
)
```

のようなコードになり、ページそのものよりも「共通化の仕組み」を理解する作業が必要になる。

これは今回目指す方向ではない。

------------------------------------------------------------------------

## 4. 基本構造：1ページ = 1クラス = 1ファイル

今後のダッシュボードでは、基本的にページ（Tab）単位でクラスを分離する。

例：

``` text
app.py
├─ daily_tab.py
├─ alarm_tab.py
├─ production_tab.py
└─ machine_tab.py
```

各ファイルには、そのページに必要なものをまとめて持たせる。

例えば `DailyTab` なら、

``` text
DailyTab
├─ Search frame
├─ Chart frame
├─ Table frame
├─ 初期設定
├─ DB検索
├─ search()
├─ update_chart()
└─ update_table()
```

という構造にする。

重要なのは、

> **そのページを理解したければ、そのファイルを見ればよい。**

という状態を保つことである。

------------------------------------------------------------------------

## 5. クラスで名前空間を分離する

今回の改造で特に大きなメリットだったのが、各ページをクラスにしたことである。

以前のようにグローバル変数中心で作ると、

``` python
daily_tree
alarm_tree

daily_canvas
alarm_canvas

daily_figure
alarm_figure
```

のように、ページ名を変数名へ付ける必要が出てくる。

ページが増えるほど名前も増える。

しかし各ページをクラスにすれば、それぞれのクラス内で堂々と同じ名前を使える。

``` python
self.tree
self.canvas
self.figure
self.ax

self.machine_combo
self.start_entry
self.end_entry
```

メソッドも同様である。

``` python
self.search()
self.update_chart()
self.update_table()
```

`DailyTab` と `AlarmTab` の両方に `self.tree` があっても衝突しない。

これにより、

-   名前を考える負担が減る
-   コードが読みやすい
-   VS Code の補完が使いやすい
-   テンプレートをコピーしやすい

という大きなメリットが得られる。

------------------------------------------------------------------------

## 6. コピペは悪ではない

今回の重要な結論の一つ。

> **コピペそのものは悪ではない。**

問題なのは、

-   どこからコピーしたか分からない
-   古いコードをコピーする
-   バグを含むコードをコピーする
-   コピー元がバラバラ
-   コピー後に大量の名前変更が必要

といった「管理されていないコピペ」である。

逆に、

> **品質の良いテンプレートをきちんと管理して、そこからコピーする**

のであれば、非常に実用的な開発方法になる。

------------------------------------------------------------------------

## 7. 「コピペ元となるテンプレート」を管理する

今後、新しいダッシュボードページを追加するときは、完成度の高いTabをテンプレートとして利用する。

テンプレートには例えば以下を含める。

``` text
Search frame
Chart frame
Table frame
Initial settings
DB access
search()
update_chart()
update_table()
単体テスト用 __main__
```

新しいページを作るときは、

``` text
テンプレートをコピー
        ↓
クラス名を変更
        ↓
SQLを変更
        ↓
Chartを変更
        ↓
Tableの列を変更
        ↓
単体テスト
        ↓
app.pyへ追加
```

という流れにする。

重要なのは、**コピー後に大量の変数名を付け替えないこと**である。

クラス内部では、

``` python
self.tree
self.ax
self.canvas
self.search()
```

などの名前をそのまま使えばよい。

クラスによって名前空間が分かれているため、わざわざ、

``` python
daily_tree
alarm_tree
production_tree
```

のように変更する必要がない。

------------------------------------------------------------------------

## 8. 「名前を付け替えるための共通化」は避ける

共通化した結果、ページごとに大量の識別名や設定名を渡す必要が出るのであれば、その共通化は慎重に考える。

例えば、

``` python
GenericDashboardTab(...)
```

のような万能クラスを作り、

-   タイトル
-   DB列名
-   Chart種類
-   Table列
-   軸名
-   並び順
-   検索条件
-   表示方法
-   ページ固有オプション

などを大量に外部から指定するようになると、ページのコードを読むだけでは動作が分からなくなる。

今回の方針では、

> **ページ固有の処理はページ自身に書く。**

これを基本とする。

少しコードが重複していても、具体的で読みやすい方を優先する。

------------------------------------------------------------------------

## 9. 本当に困ってから共通化する

将来5ページになるからといって、最初から5ページを想定した巨大な共通基盤を作らない。

まず実際にページを作る。

例えば、

``` text
DailyTab
AlarmTab
ProductionTab
MachineTab
TrendTab
```

と増えていったとする。

その段階で、

> 「この処理、5ファイル全部まったく同じだな」

あるいは、

> 「同じ修正を5ファイルに入れるのが面倒になってきたな」

と感じた部分だけを共通化する。

つまり、

``` text
予測して共通化する
```

よりも、

``` text
実際の重複を確認する
        ↓
本当に困る
        ↓
必要な部分だけ共通化する
```

という順番を重視する。

これなら過剰な抽象化を防げる。

------------------------------------------------------------------------

## 10. 良いDRYと悪いDRYを区別する

DRYそのものを否定するわけではない。

今回採用した `TABLE_COLUMNS` のような仕組みは良い例である。

``` python
TABLE_COLUMNS = {
    "date": {
        "text": "Date",
        "width": 700,
        "anchor": tk.W,
    },
    "alarm_count": {
        "text": "Count",
        "width": 100,
        "anchor": tk.CENTER,
    },
}
```

これを使って、

``` python
for column_id, settings in TABLE_COLUMNS.items():
    self.tree.heading(
        column_id,
        text=settings["text"],
    )

    self.tree.column(
        column_id,
        width=settings["width"],
        anchor=settings["anchor"],
    )
```

とする。

これは、

-   設定場所が分かりやすい
-   列追加が簡単
-   コードの意図が見える
-   抽象化しても具体性を失わない

ため、KISSとDRYを両立できている。

つまり、

> **読みにくくならないDRYは積極的に使う。**
>
> **読みにくくなるDRYは無理に使わない。**

という判断をする。

------------------------------------------------------------------------

## 11. 各ページは単体実行できるようにする

各Tabファイルには、

``` python
if __name__ == "__main__":
```

を用意し、単体でF5実行できるようにする。

例えば、

``` python
if __name__ == "__main__":
    root = tk.Tk()

    daily_tab = DailyTab(root)
    daily_tab.pack(
        fill=tk.BOTH,
        expand=True,
    )

    root.mainloop()
```

のようにする。

これにより、

``` text
DailyTab単体では正常
        ↓
app.pyに組み込むと異常
```

なら、

> 問題はDailyTab本体ではなく、組み込み側にある可能性が高い

と切り分けられる。

ページ追加時にも、

``` text
新ページを作る
    ↓
単体F5
    ↓
完成を確認
    ↓
メインアプリへ組み込む
```

という安全な開発ができる。

------------------------------------------------------------------------

## 12. app.pyは「司令塔」に徹する

メインの `app.py` に、DB検索、Chart更新、Table更新などを書かない。

`app.py` の仕事は基本的に、

``` text
メインウィンドウを作る
Notebookを作る
各Tabを作る
Notebookへ追加する
終了処理を行う
mainloop()を開始する
```

だけにする。

イメージ：

``` python
daily_tab = DailyTab(notebook)
alarm_tab = AlarmTab(notebook)

notebook.add(
    daily_tab,
    text="日別",
)

notebook.add(
    alarm_tab,
    text="アラーム別",
)
```

新ページ追加も、

``` python
production_tab = ProductionTab(notebook)

notebook.add(
    production_tab,
    text="生産実績",
)
```

程度で済む状態を目指す。

これにより、`app.py` を見れば、

> **このアプリにはどんなページがあるのか**

がすぐ分かる。

------------------------------------------------------------------------

## 13. 新しいページを追加するときの標準手順

今後の基本手順は以下とする。

1.  管理しているTabテンプレートをコピーする。
2.  ファイル名とクラス名を新しいページ用に変更する。
3.  `TABLE_COLUMNS` を変更する。
4.  SQLをページの目的に合わせて変更する。
5.  `update_chart()` を変更する。
6.  `update_table()` を変更する。
7.  必要ならSearch条件を追加する。
8.  ファイル単体でF5実行して確認する。
9.  `app.py` でimportする。
10. Notebookへ追加する。
11. アプリ全体で動作確認する。

基本的には、

> **「新しいページ追加して」→「あいよっ！」→テンプレートをコピー**

できる状態を維持する。

------------------------------------------------------------------------

## 14. 改造時は一気に変更しない

今回のリファクタリングでは、一度にすべてを書き換えず、小さく進めた。

例えば、

``` text
Search frameを作る
↓
F5

Chart frameを作る
↓
F5

Table frameを作る
↓
F5

DB検索を追加
↓
F5

Chart更新を追加
↓
F5

Table更新を追加
↓
F5

メインアプリへ組み込む
↓
F5

旧コードを少しずつ削除
↓
F5
```

という進め方をした。

この方法なら、不具合が発生しても、

> 「直前の変更が怪しい」

と判断しやすい。

大規模改造ほど、変更単位を小さくする。

------------------------------------------------------------------------

## 15. VS Codeの補完を大切にする

今回の方針では、VS Codeの補完が自然に効く構造を重視する。

例えば、

``` python
self.ax.
```

まで入力したときに、matplotlibのAxesのメソッド候補が表示される。

``` python
self.tree.
```

ならTreeviewのメソッド候補を確認できる。

これは単なる入力補助ではない。

> **「このオブジェクトには本当にこのメソッドがあるのか？」を確認する安全装置**

として利用できる。

過剰な動的生成や抽象化によって補完が弱くなる構造は、特別なメリットがない限り避ける。

------------------------------------------------------------------------

## 16. pywebview等でも同じ考え方を使える

今回の考え方はTkinter専用ではない。

将来pywebviewなどでダッシュボードを作る場合でも、

``` text
AlarmPage
DailyPage
ProductionPage
MachinePage
```

のようにページ単位で独立させる考え方は利用できる。

ユーザーから見れば1つのダッシュボード（SPA的な操作感）でも、内部ではページごとに独立していてよい。

特にページ間で複雑な状態共有が必要ない業務ダッシュボードでは、

> **外から見ると一体型、内部は独立型**

という構造は扱いやすい。

------------------------------------------------------------------------

## 17. 今回の判断基準

今後、共通化するかコピペするか迷ったら、次の質問をする。

### その共通化でコードは本当に分かりやすくなるか？

YESなら共通化を検討する。

NOなら無理に共通化しない。

### 同じ修正を何度も行うことが実際に問題になっているか？

まだ問題になっていないなら、急いで抽象化しない。

### ページ単体を見て処理内容を理解できるか？

できる状態をできるだけ維持する。

### VS Codeの補完が自然に使えるか？

補完が使える具体的な構造を好む。

### 半年後の自分が読めるか？

「今の自分が賢く書けるか」ではなく、

> **「忘れた自分が簡単に読めるか」**

を重要視する。

------------------------------------------------------------------------

## 18. 今回の開発方針を一言でまとめる

今回たどり着いた考え方は、

> **ページをクラス単位で独立させ、良いテンプレートを管理し、罪悪感なくコピーする。共通化は、本当に必要になった部分だけ後から行う。**

というものである。

DRYだけを目的にしない。

KISSだけを理由に雑なコードにもしない。

必要なところではDRYを使い、具体性を失いそうならKISSを優先する。

------------------------------------------------------------------------

# 最終方針

## 冷静にDRY、情熱的にKISS、罪悪感ゼロでコピペ。

そして、

> **コピペ元となるテンプレートをきちんと管理する。**

これを今後作るダッシュボードアプリの基本方針とする。
